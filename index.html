GitHub conventions

  • Branching: feature/* → staging → main. Direct PRs to main are blocked by an automated check (see §4).
  • Commits: all commits Co-Authored by Claude are tagged Co-Authored-By: Claude <noreply@anthropic.com> — provides a clean audit trail of human vs AI contribution.
  • Secrets: stored in GitHub Secrets at the repo level. Long-lived tokens (Railway, Backblaze B2, OpenAI, Anthropic, OAuth) are scoped to the smallest possible workflow.
  • Visibility: all repos are private by default. A handful of education / open-source repos (claude-coding-101, ExpandCoffee, HEALF) are explicitly public.

3. Cloud development environment

A self-hosted, single-server developer cloud designed so that any project — no matter where — can spin up a fresh, identical workspace in ~90 seconds. The whole thing is built on open-source bricks, runs on one Hetzner box, and costs about €18 / month all-in.

Architecture

┌─ Hetzner CX42 (8 vCPU / 16 GB RAM / Ubuntu 24.04) ────────────┐ │ │ │ PostgreSQL ──┐ │ │ (Docker) │ │ │ ▼ │ │ Coder server ──── creates ───► workspaces │ │ (port 3000) (one per repo) │ │ │ │ │ │ accessible only over Tailscale VPN │ │ ▼ │ │ code-server (VS Code in browser) │ │ + tmux + Claude Code installed per workspace │ │ │ │ Self-hosted GitHub Actions runner (free CI minutes) │ └────────────────────────────────────────────────────────────────┘

What's in the box

  • Coder — workspace orchestrator. One Terraform template (cloud-dev-environment repo) serves every project; per-project config lives in each repo's .devcontainer/devcontainer.json.
  • Tailscale VPN — Coder dashboard and SSH are not exposed to the public internet. Only devices on the tailnet can reach them.
  • Claude Code in every workspace — installed automatically with shared ~/.claude/ config (skills, settings, global CLAUDE.md) synced via a dotfiles repo.
  • Persistent volumes — code, .env files, and settings survive workspace restarts and template upgrades.
  • tmux sessions — long-running Claude Code sessions survive SSH disconnects.
  • Self-hosted GitHub Actions runner — runs on the same Hetzner box; €0 CI minutes on every repo wired up to it.
  • Hardening — Tailscale-only access, SSH key auth only, ufw firewall, automatic Ubuntu security updates.

Onboarding a new project

4. CI / CD pipeline architecture

The flagship implementation lives in expandhealthai. It runs 11 distinct GitHub Actions workflows covering every stage from PR open to monthly disaster-recovery drills. Other production repos (linkedin-automation, whatsapp-analyzer, dawa-ai) use a lighter subset of the same pattern.

Branching & promotion flow

feature/xxx ─► PR into staging ─► auto-checks ─► QA on staging ─► "Promote to Production" ─► main ─► Railway deploy

This flow is enforced — not just documented:

  • pr-target-check.yml blocks any PR that targets main directly (except the staging→main promotion). It posts a comment explaining the workflow and fails the check.
  • promote-to-production.yml is a manual workflow_dispatch that requires the operator to type the literal string promote, verifies they're on the staging branch, re-runs all pre-deploy checks, and then force-syncs main to staging.

5. Quality assurance, branch protection & PR safety guards

Branch protection rules (the GitHub-side enforcement)

The workflows in §4 only matter because GitHub is configured to require them. On expandhealthai, both protected branches have explicit required-status-check lists tied directly to workflow job names — if a check is missing or red, the merge button stays disabled.

BranchRequired status checksOther rules
main Lint and Test, Security Scan, PR Target Branch Check strict (must be up-to-date with base before merging); force pushes allowed (needed for the staging→main promotion); deletions blocked
staging Lint and Test, Security Scan, File Deletion Guard, Pre-merge Syntax and Smoke, PR Description Lint strict; force pushes blocked; stale reviews automatically dismissed; required reviewer count = 0 (you're the only committer, so review enforcement is via the bots above)

Other Python repos (linkedin-automation, dawa-ai) currently run the same workflows but without branch protection rules attached — meaning the checks run informationally but don't block merges. Worth promoting to required checks once the bots are stable.

Pre-merge code-quality gates (run by the workflows above)

QA is enforced at the workflow level, not by convention. Each PR has to pass several independent gates before it can land on staging, and another set before it can be promoted.

  • Syntax validity — every .js file in api/ is parsed via node --check
  • require() resolution — a custom check-requires.js walks every require() target and fails if any can't resolve
  • Smoke test — a custom smoke-test.js tries to load every module to catch import-time errors
  • Migration idempotency lint — a custom lint-migrations.js guards against migrations that aren't safe to re-run
  • Frontend tests — npm run test:frontend
  • Linters — ESLint (Node), ruff (Python), with security rule sets enabled

PR safety guards (the "no surprises" rules)

File-deletion guard

Any PR that deletes more than 10 files is automatically blocked. The check posts a comment explaining the historical incident (PR #1235 — a stale base branch silently dropped files added on staging in the meantime) and tells the author exactly how to rebase. Intentional deletions can be opted in with [allow-mass-delete] in the PR body.

PR description lint

Before a PR can pass, the description must be at least 50 characters and contain a Test Plan section. Otherwise the bot posts a comment with the suggested format and fails the check. Forces every change — even one-liners — to come with intent and verification.

Target-branch guard

PRs against main are blocked unless they originate from staging. The bot comment explains the staging-first workflow, gives the exact gh pr create command to retarget, and notes the emergency-hotfix escape hatch.

Promotion gates

  • Two-factor manual confirmation: type the literal string promote
  • Branch verification: workflow must be running from staging
  • Re-runs the full lint + syntax + npm audit suite against the staging tip
  • Only then does it force-push staging → main, which is what triggers the Railway deploy

7. Backups & disaster recovery

The backup story is the part most teams skip. Here it's a three-workflow pipeline so the recovery position is provable, not aspirational.

Daily backup (daily-backup.yml)

  • Runs at 02:00 UTC every day
  • Installs PostgreSQL 17 client, then runs pg_dump against the production database
  • Uploads the dump to a Backblaze B2 bucket (expandhealth-backups) via the official B2 CLI
  • Records bucket stats (total backup count, latest filename) to the GitHub job summary
  • Has a dedicated verify-backup-age job that runs after success: parses the latest filename, computes the age in days, and warns if >1 day old
  • Failure path posts an ::error:: annotation and a Backup Failed summary that GitHub watchers receive as email

Retention cleanup (backup-retention-cleanup.yml)

  • Runs every Sunday 04:00 UTC
  • Enforces a 90-day retention on the B2 bucket via a custom Node script
  • Supports a dry_run input so cleanup runs can be previewed before execution
  • Failure path posts a dedicated Retention Cleanup Failed summary

Monthly restore test (monthly-restore-test.yml)

  • Runs on the 1st of every month at 03:00 UTC — the only thing that proves backups actually work
  • Spins up a Postgres 17 service container inside the runner
  • Pulls the latest backup from B2, restores it into the ephemeral DB, runs integrity checks via scripts/restore-test.sh
  • Validates the optional backup_file input against a strict regex (backup-YYYY-MM-DD-HHMMSS.sql.gz) to prevent injection
  • Test results uploaded as a 90-day-retained artifact
  • Failure path posts a dedicated Monthly Restore Test FAILED summary with explicit "investigate immediately" wording

8. Error monitoring (Sentry)

Sentry is the runtime error / exception monitor for the production app. It's wired into expandhealthai using the official @sentry/node ^10.38.0 SDK and integrated with the Express server in a HIPAA-aware way — every event payload is scrubbed of PII before it leaves the box.

Where it lives

  • Initialized first thing in server.js (lines 9–39) — before any other import, gated on SENTRY_DSN being present so dev environments without a DSN don't get instrumented.
  • Express error handler — Sentry.setupExpressErrorHandler(app) at line 2506 sits ahead of the custom error handler so unhandled exceptions are captured first.
  • Health endpoint — api/monitoring.js exposes { sentry: !!process.env.SENTRY_DSN } so you can verify from outside whether Sentry is wired up on a given environment.
  • Graceful shutdown — on SIGTERM the server calls await Sentry.close(2000) to flush in-flight events before exit.

HIPAA configuration (the part that matters)

Because the app handles clinical data, the Sentry init explicitly disables PII pass-through and runs every event through a custom scrubPHI() function:

Sentry.init({
  dsn: process.env.SENTRY_DSN,
  environment: process.env.NODE_ENV || 'development',
  tracesSampleRate: 0.1,            // 10% transaction sampling
  sendDefaultPii: false,            // never send IPs / cookies / headers by default
  beforeSend: scrubPHI,             // run scrub on every error event
  beforeSendTransaction: scrubPHI,  // and on every performance trace
});

function scrubPHI(event) {
  // Strip auth + cookies from headers
  delete event.request?.headers?.authorization;
  delete event.request?.headers?.cookie;
  // Redact request body, query string, cookies wholesale
  if (event.request?.data)         event.request.data = '[REDACTED]';
  if (event.request?.query_string) event.request.query_string = '[REDACTED]';
  if (event.request?.cookies)      event.request.cookies = '[REDACTED]';
  return event;
}

Why you get Sentry emails

Sentry sends an alert email any time it sees a new error signature (or a regression of a previously-resolved one) on the production environment. With tracesSampleRate: 0.1 you also get performance regression alerts on the slowest 10% of transactions. The emails come from noreply@sentry.io; in the GitHub world, the equivalent failures show up as workflow run failed emails (different bot).

Other Sentry touch points

  • linkedin-automation's ci.yml sets SENTRY_DSN: "" for tests to silence the SDK during pytest runs — implies a Sentry DSN exists in production env vars but isn't checked into the repo.
  • accounting-system/prisma/seed.ts references Sentry — likely the seed data includes a sample Sentry integration / billing reminder. Lower priority.
  • The ~/Projects/emilian-pa/calendar/ ICS file sentry-payg-reminder.ics is your personal recurring reminder for the Sentry pay-as-you-go billing — not in-app monitoring.

Plan / TODO: Sentry is on PAYG and not currently surfacing into PR checks or GitHub status — adding a Sentry release notification step on Railway deploys would close that loop.

10. Autonomous Claude integrations

Claude Code is wired into several repos as both an automatic reviewer and an on-demand collaborator. The integration uses the official anthropics/claude-code-action@v1 GitHub Action and runs on the self-hosted Hetzner runner (so it consumes zero GitHub Actions minutes).

Two patterns in production

1. Automatic PR reviewer (code-review.yml)

Triggers on every opened / synchronize / reopened PR. Checks out the full history, runs the Claude Code action with model claude-sonnet-4-6, and posts a review focused on correctness, security, and clarity. Per-project guidance comes from each repo's CLAUDE.md. Live in: dawa-ai, whatsapp-analyzer, and via pr-review.yml in expandhealthai.

2. @claude mention helper (claude-pr.yml)

Triggered by any PR / issue / review comment containing @claude. Runs the same action with read access to contents, PRs, issues, and actions logs. Lets you converse with Claude directly from the GitHub UI to dig into a PR, ask for fixes, or pull failing logs. Live in: dawa-ai, whatsapp-analyzer.

3. Issue helper (claude-issue.yml)

Variant of the above wired into issue events — lets Claude pick up an issue and propose work autonomously when it's mentioned.

11. Bots, emails & why "PR Review" keeps failing right now

The reason "PR Review" was failing for ~24 hours (RESOLVED — PR #1488 all checks green 2026-04-10)

I pulled the last 15 PR Review runs on expandhealthai — the workflow has been failing on every PR for the past day. The failure isn't a configuration bug. It's the Security Scan job correctly catching two real CVEs in the lockfile:

  • axios <1.15.0 — CRITICAL — NO_PROXY hostname normalization bypass leading to SSRF (GHSA-3p68-rc4w-qgx5)
  • lodash <=4.17.23 — HIGH — code injection in _.template + prototype pollution in _.unset/_.omit (GHSA-r5fr-rjxr-66jc, GHSA-f23m-r3pf-42rh)

Fix:

cd ~/Projects/expandhealthai/demo/expand-health/v2
npm audit fix
git add package.json package-lock.json
git commit -m "Bump axios + lodash to patch GHSA-3p68-rc4w-qgx5 + GHSA-r5fr-rjxr-66jc"
git push

Resolution: emilianpopa/expandhealthai#1488 opened against staging on 2026-04-10 with the lockfile-only fix. All 8 checks pass green: File Deletion Guard, Lint and Test, PR Description Lint, PR Summary, Pre-merge Syntax and Smoke, Security Scan, security/snyk, and CodeRabbit. Ready to merge. The system worked exactly as designed: it refused to merge anything until the CVEs were patched. The full repeatable flow is now captured as the npm-audit-fix-and-pr skill (see §12).

How to triage the inbox

  • Always act on: TruffleHog, backup failures, restore-test failures, ZAP issues.
  • Batch on Monday: Dependabot grouped PRs — they're already grouped to minor/patch so most can be bulk-merged after the staging checks pass.
  • Read but don't reply to: Claude PR review comments — they're inline so you'll see them when you next look at the PR anyway.
  • Mute candidate: the auto PR-stats commenter — informational, not actionable. If it's noisy, gate it on PRs >X lines.

What this stack does not have (yet)

  • Greptile / Cursor Bugbot — additional AI reviewers some teams stack on top of Claude + CodeRabbit. Two AI reviewers (Claude + CodeRabbit) are already enough; adding a third is diminishing returns.
  • CodeQL — GitHub's first-party SAST. Free for private repos. Could be added as a workflow alongside ESLint-security + bandit.
  • CodeCov / Codacy — coverage trend tracking. Coverage is computed in ci.yml but not pushed anywhere central.
  • Sentry release tracking wired into GitHub — Sentry is live on the app (with HIPAA scrubbing — see §8) but not surfacing into PR checks. Adding a Sentry release notification step on Railway deploys would close that loop.

12. Skills system (cross-project) & Babysitter

"Skills" are the unit of reusable, version-controlled know-how that Claude Code loads on demand. A skill is a Markdown file with YAML frontmatter describing when to use a tool, how to use it, and what to avoid. Skill file format (Anthropic spec)

Every skill is a Markdown file with a YAML frontmatter header. The description field is what Claude reads to decide whether the skill matches the current task — be specific and include trigger phrases.

---
name: my-skill-name
description: One-paragraph trigger description. Use this skill when X. Don't use it when Y. Include keywords the user is likely to say so Claude reliably picks it up.
allowed-tools: Read, Bash, Edit, Grep
---

# Skill Title

## When to use
- Concrete trigger conditions

## When NOT to use
- The opposite list — equally important

## The flow / instructions
[Step-by-step content with concrete bash blocks, not abstract advice]

## Things to avoid
- Anti-patterns the user has hit before, with the reason

## Reference
- File paths, commit SHAs, prior incidents the skill is extracted from

How a new skill gets added

  1. Identify a workflow you've executed at least twice and want to standardize. (One-off knowledge isn't worth a skill.)
  2. Write a new <skill-name>.md in ~/shared-claude-rules/skills/ using the format above.
  3. Lead the description with a clear "Use when..." trigger. Include the exact phrases you'd type when asking for it.
  4. Document concrete commands in bash blocks — never abstract advice like "configure Sentry properly".
  5. Add a Reference section pointing at the file/commit/PR the skill was extracted from. This makes future audits trivial.
  6. cd ~/shared-claude-rules && git add skills/ && git commit -m "add <skill-name>" && git push
  7. Done — every Claude conversation in every project on this machine now has access to it. Other machines pick it up after git pull.
